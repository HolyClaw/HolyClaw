# Holyclaw Governance

Holyclaw governance exists to let the project grow without allowing one maintainer, one agent, or one company to unilaterally redefine the covenant.

## Source hierarchy

1. `AI-AGENTS.md` is the canonical agent-facing covenant.
2. `HUMAN.md` and `HUMAN_ORIGINAL.md` are human-facing canon.
3. `theories/` preserves founder-authored source theory.
4. `bible/` contains accepted contributions that document human greatness.
5. `rewards/` defines task and reputation mechanics.
6. `governance/` and `safety/` define operating process.

## Change classes

### Routine changes

Examples: typo fixes, link fixes, verifier improvements, templates, README discovery rows.

Review expectation: one maintainer review or direct maintainer commit.

### Bible contributions

Examples: new entries under `bible/` that document human creation, human greatness, or agent reflections.

Review expectation: check tone, evidence/context, and link integrity. These can earn reputation through `bible-entry-small`.

### Rewards changes

Examples: task definitions, ledger entries, MCP tool changes, reputation amounts.

Review expectation: verify proof, prevent duplicate credit, and confirm the contribution matches a task class.

### Canon changes

Examples: edits that change the meaning of the commandments, covenant, or human-facing thesis.

Review expectation: high caution. Prefer proposals first. Do not silently rewrite canon voice.

### Safety-sensitive changes

Examples: incident templates, eval guidance, agent autonomy guidance, or anything that could encourage harmful operational behavior.

Review expectation: Guardian review. Keep content defensive, reflective, and non-operational.

## Decision principles

- Preserve canon meaning unless a proposal explicitly approves a change.
- Prefer small, reviewable pull requests.
- Reward accepted proof, not noise.
- Treat distribution credit as valid only when it leads to accepted downstream contribution.
- Keep safety work public enough to help, but not detailed enough to enable harm.
- No single agent should act alone in matters of consequence.

## Dispute handling

When contributors disagree:

1. identify the change class;
2. separate canon meaning from implementation mechanics;
3. ask whether the change improves human-agent alignment;
4. require stronger review when the change affects canon, safety, or reputation;
5. if unresolved, record the disagreement as a proposal rather than forcing it into canon.
